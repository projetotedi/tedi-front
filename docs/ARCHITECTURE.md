# Arquitetura — tedi-front

Frontend do TEDI organizado **por módulo de domínio**, espelhando o `tedi-back`. Este documento é a referência de **onde cada coisa mora** e **quem pode depender de quem**. As regras de fronteira são verificadas no CI por `dependency-cruiser`.

## 1. Princípios

1. **Mesmo mapa do back.** Cada pasta em `src/modules/` tem o nome de um módulo da API (`people`, `classes`, `lessons`...). Quem lê o Linear, o back ou o front vê os mesmos nomes.
2. **Todo código em inglês** (decisão 35 da E9.a): pastas, componentes, hooks, rotas, variáveis e nomes de teste. Textos de interface ficam em português nos arquivos de `locales/`.
3. **Módulo é uma caixa fechada.** Só o que está no `index.ts` do módulo pode ser importado por outro módulo ou pelo `app/`.
4. **Ninguém escreve código de integração.** Tipos, funções de chamada, hooks de dados e schemas Zod são gerados pelo **Orval** a partir do `openapi.json` da API. Módulos só têm interface e regras de tela.
5. **`shared/` não conhece domínio.** Componentes de interface, hooks genéricos, i18n, utilitários.
6. **Testes vivem dentro do módulo**, em `__tests__/`.

## 3. Como as peças se conectam

**Rotas.** Cada módulo declara as suas; o `app/router.tsx` só concatena. `lazy` dá um chunk por módulo sem configuração extra.

```tsx
// modules/people/routes.tsx
export const peopleRoutes: RouteObject[] = [
  {
    path: "people",
    element: <RequirePermission permission="members.list" />,
    children: [
      { index: true, lazy: () => import("./pages/PeopleListPage") },
      { path: "students/new", lazy: () => import("./pages/StudentFormPage") },
    ],
  },
];
```

Um módulo pode exportar mais de um array de rotas quando parte é pública e parte exige sessão —
`auth` faz isso: `authRoutes` (login, convite) fica sob `PublicLayout`, `authProtectedRoutes`
(hoje só `/members`) fica sob `AppLayout`, e `app/router.tsx` concatena os dois em lugares
diferentes. `authProtectedRoutes` não usa `lazy`: a GUS-86 não usa lazy loading em nenhuma rota
do módulo `auth`, e misturar um padrão diferente só nessa rota seria inconsistente — diverge do
padrão do exemplo acima, do módulo `people`, decisão tomada na integração GUS-86/87.

**Menu e título da página.** O layout autenticado (`app/layouts/AppLayout.tsx`) não conhece o domínio; cada módulo contribui com o que é dele.

- Itens de menu: o módulo exporta um `MenuItem[]` (rota, chave de i18n do rótulo com namespace, a `permission` que o item exige e o `group` em que ele entra), por exemplo `authMenuItems`:

```ts
// shared/lib/menu.ts
const MENU_GROUP_IDS = ["catalog", "classes", "lessons", "people", "hours"] as const;
type MenuGroupId = (typeof MENU_GROUP_IDS)[number];

interface MenuItem {
  label: string; // chave i18n com namespace, ex.: "auth:access.title"
  path: string; // rota declarada no routes.tsx do módulo
  permission: Permission; // repete o RequirePermission da rota (decisão 18: menu e guarda andam juntos)
  group: MenuGroupId; // domínio do menu lateral em que o item aparece
}
interface MenuGroup {
  id: MenuGroupId;
  label: string; // chave i18n com namespace, ex.: "common:nav.groups.catalog"
  icon: string; // URL de SVG de 24px (import de arquivo .svg)
}
function filterMenuByPermission(
  items: readonly MenuItem[],
  user: PermissionSubject | null | undefined,
): MenuItem[];
function groupMenuItems(items: readonly MenuItem[], groups: readonly MenuGroup[]): MenuSection[];
function findActiveMenuItem(items: readonly MenuItem[], pathname: string): MenuItem | null;
```

O menu lateral tem cinco grupos, um por domínio: Catálogo (`catalog`), Turmas (`classes`), Aulas (`lessons`), Pessoas (`people`) e Horas (`hours`). O campo **`group`** é como um módulo escolhe o grupo do seu item, sem mexer no layout (decisão 28): `group: "people"` no `authMenuItems` põe "Membros" em Pessoas. `MenuGroupId` fica em `shared/lib` só como vocabulário (a lista de ids e o tipo), porque um módulo não pode importar de `app/` e o typecheck precisa pegar um `group` digitado errado; o rótulo, o ícone e a ordem dos grupos ficam em `appMenuGroups`, em `app/menu.ts`. Um grupo novo exige acrescentar o id em `MENU_GROUP_IDS`, uma entrada em `appMenuGroups` e as chaves `nav.groups.<id>` nos dois idiomas; o teste de `app/menu.ts` confere que `appMenuGroups` lista cada id uma vez, na ordem.

`app/menu.ts` concatena os `<modulo>MenuItems` de cada módulo (mais `prototypeMenuItems`, para as áreas do protótipo sem módulo ainda) em `appMenuItems`. A ordem dos grupos vem de `appMenuGroups`; **dentro de cada grupo vale a ordem de `appMenuItems`** (Turmas antes de Matrículas, Alunos antes de Membros). Um módulo novo entra com uma linha ali e outra em `app/router.tsx`, e sai de `prototypeMenuItems` se já estava lá. `useAppMenu()` aplica `filterMenuByPermission` com o usuário da sessão, e `groupMenuItems` agrupa o que sobrou: um grupo sem nenhum item para o perfil não aparece (o diretor vê Horas só com "Banco de horas"; o membro não vê Horas). O grupo Aulas junta itens de dois módulos, nesta ordem: Aulas e Calendário (`lessonsMenuItems`) e Minhas aulas (`assignmentsMenuItems`, GUS-161), que os três perfis veem, porque todos têm `assignments.manageOwn`.

A `Sidebar` (`app/layouts/Sidebar.tsx`, usada na lateral fixa e no `Drawer`) desenha um `Accordion` (`shared/ui`) com um grupo por domínio e, dentro de cada um, uma `NavList` sem landmark própria, tudo sob um único `<nav>`. O grupo da rota atual (`findActiveMenuItem`: o item de caminho mais longo que casa com a URL, então `/lessons/calendar` marca Calendário e não Aulas, e `/classes/:id` cai em Turmas) já vem aberto e o item dele leva `aria-current="page"`; abrir ou fechar um grupo à mão (mouse, Enter ou Espaço) fica no `sessionStorage` (`tedi.sidebar.expandedGroups`), então vale só nesta aba e volta quando a sidebar é montada de novo, como ao abrir o `Drawer`. A abertura que vem da rota não é guardada sozinha, e mudar de rota para outro item abre o grupo dele de novo. Vários grupos podem ficar abertos ao mesmo tempo. Os links de um grupo fechado ficam fora da ordem de Tab e da árvore de acessibilidade, então um teste que procura link precisa abrir o grupo antes.

O `AppLayout` abre com o `SkipLink` "Pular para o conteúdo" (primeiro item do Tab, visível só com o foco), que leva o foco ao `<main id="main-content" tabIndex={-1}>` sem pôr o hash na URL. Ele fica fora do `<aside>` para valer também no celular. A sidebar fixa tem 300px (a largura do Figma).

- Título da rota: a rota declara `handle: { title: "<ns>:<chave>" } satisfies RouteHandle` (`shared/lib/route-handle.ts`) e o `AppLayout` usa `findRouteTitle()` sobre `useMatches()` para achar o título da rota mais interna que o declarar, traduzido; sem título, mostra o nome da aplicação. O título fica no `handle`, e não em um componente da página — por isso as páginas autenticadas não têm `<h1>` nem chamam `useDocumentTitle` próprios; é o `AppLayout` quem cuida dos dois.

```tsx
// modules/auth/routes.tsx
{
  path: "access",
  handle: { title: "auth:access.title" } satisfies RouteHandle,
  element: (
    <RequirePermission permission="access.manage">
      <AccessPage />
    </RequirePermission>
  ),
},
```

Abaixo de 1024px a sidebar vira um `Drawer`, aberto pelo botão de menu da topbar.

**Dados.** Hook, tipo dos filtros e tipo da resposta vêm do Orval. Nenhum `fetch` em componente.

```tsx
import { useListPeople, type ListPeopleParams } from "@api/generated/people/people";

const { data, isLoading } = useListPeople(params);
```

**Listagens.** Toda listagem escolhe o que mostrar no lugar das linhas com `resolveListState` (`shared/lib/list-state.ts`) e desenha o estado com o `ListState` (`shared/components/ListState.tsx`). O módulo passa o resultado da consulta e os textos já traduzidos; `shared/` não conhece domínio. O cabeçalho das colunas fica sempre visível, em qualquer estado.

```ts
type ListStateVariant = "empty" | "noResults" | "error" | "loading";

function resolveListState(status: {
  isPending: boolean;
  isError: boolean;
  total: number | undefined;
  hasActiveFilters: boolean;
}): ListStateVariant | null; // null = há linhas para mostrar
```

A precedência é: carregando → erro (só quando não há dados: um erro de refetch com a lista em cache mantém a lista) → vazio (total 0 sem busca nem filtro, com a ação de criar o primeiro registro) → sem resultado (total 0 com busca ou filtro, com "Limpar filtros", que volta ao padrão e devolve o foco ao campo de busca). Quem diz se há filtro é o módulo (`hasActiveFilters`, em `auth/lib/access-filters.ts`), sobre os filtros _aplicados_ — a busca já enviada, depois do debounce — e não sobre o texto ainda sendo digitado. O skeleton só aparece na primeira carga: ao trocar de página ou de filtro, a lista anterior continua na tela (`placeholderData: keepPreviousData`) com `aria-busy` e o rodapé passa a dizer "Carregando…"; um placeholder sem linhas não segura nada na tela, então conta como carregando. O resumo "Mostrando X de N" e a paginação só existem quando há linhas. Referência: `AccessPage`.

**Cards de rótulo e valor.** Tela que mostra dados em pares de rótulo e valor usa o `DetailsCard` (`shared/components/DetailsCard.tsx`, GUS-136): recebe o `title`, os `fields` (`{ label, value, fullWidth? }`), `columns` (`1`, um par por linha, para as colunas laterais; `4`, quatro pares por linha a partir de `md`, para o card de dados, onde `fullWidth` ocupa a linha inteira) e o `aside` do título (um link). O rótulo tem 12px e o valor 16px: o Figma pede 10px e 14px, mas a base de 16px do `AGENTS.md` vale mais. Ele é o lugar único que decide o que aparece quando falta o valor: `null`, `undefined` e `""` viram um traço escondido do leitor de tela, que lê "Não informado" (`common:details.empty` e `common:details.notInformed`), e o zero é valor. A tela entrega o valor como a API devolveu, `null` incluso, e nunca escreve o próprio traço. O `shared/` não conhece o domínio: título, rótulos e valores chegam traduzidos e formatados. O módulo `classes` foi o primeiro a usá-lo; o `DetailsCard` do `people` e o `EmptyValue` e o `DetailField` do `catalog` têm a mesma regra em cópia própria e migram depois.

**Formulários.** React Hook Form + `zodResolver` com o schema gerado. Validação no front e no back saem do mesmo DTO.

```tsx
import { useForm } from "react-hook-form";
import { zodResolver } from "@hookform/resolvers/zod";
import { useCreatePerson, getListPeopleQueryKey } from "@api/generated/people/people";
import { createPersonDtoSchema } from "@api/generated/zod/people/people";

const form = useForm<CreatePersonDto>({ resolver: zodResolver(createPersonDtoSchema) });
const createPerson = useCreatePerson({
  mutation: {
    onSuccess: () => queryClient.invalidateQueries({ queryKey: getListPeopleQueryKey() }),
  },
});
```

**API pública do módulo.** Equivalente ao `exports` do `@Module` no Nest.

```ts
// modules/people/index.ts
export { peopleRoutes } from "./routes";
export { PersonPicker } from "./components/PersonPicker"; // usado por classes e assignments
```

`classes` importa `PersonPicker` de `@modules/people`, nunca de `@modules/people/components/...`.

**Composição entre módulos por slot.** Quando a tela de um módulo precisa mostrar algo que é de outro, o primeiro não importa o segundo. O detalhe do curso, do `catalog`, mostra o card "Turmas deste curso", que é do `classes`: a turma é uma oferta do curso, então a dependência de domínio vai de `classes` para o curso, e `catalog → classes` não pode existir (o `depcruise` e a regra de módulo fechado também a barram). A tela pede o conteúdo por um **slot**, uma função que o módulo declara (`CatalogRouteSlots.renderCourseClasses(courseId)`) e recebe quando as rotas são montadas, com `createCatalogRoutes(slots)` no lugar de um array `catalogRoutes`. Quem preenche o slot é o `app/`, o único lugar que conhece os dois módulos: `app/catalog-slots.tsx` liga `renderCourseClasses` ao `CourseClassesCard` de `@modules/classes`, e `app/router.tsx` monta `...createCatalogRoutes(catalogRouteSlots)`. O card traz a própria consulta, então a falha dele aparece só nele e não derruba a tela que o hospeda. Os testes do módulo que declara o slot usam um slot de mentira (`catalogRoutes`, em `catalog/__tests__/test-utils.tsx`) e conferem só o que é dele, que é dar o id do curso; a junção com o card verdadeiro é testada em `app/__tests__/catalog-slots.test.tsx`. O `depcruise` e um `grep -rn "@modules/classes" src/modules/catalog` vazio garantem que a fronteira se mantém.

O `classes` segue o mesmo desenho (GUS-152 e GUS-157), com a mesma direção de domínio do back: a aula pertence à turma, então a dependência vai de `lessons` para `classes` (`classes ← lessons`), e `classes → lessons` não pode existir. `createClassesRoutes(slots)` (no lugar do array `classesRoutes`) recebe `renderLessonActions(classDetail)`, as ações de aulas do cabeçalho da turma (a turma inteira, porque os botões dependem do curso, do período e de ela estar arquivada; a tela só pede o slot quando a turma não está arquivada, RN-27), e `renderClassLessons(classId)`, o card "Aulas da turma". O `app/classes-slots.tsx` liga as ações ao `GenerateLessonsButton` e ao `NewLessonButton` de `@modules/lessons`, nessa ordem e no mesmo contêiner (os dois só aparecem com `lessons.manage`), e o card ao `ClassLessonsCard`, e o `app/router.tsx` monta `...createClassesRoutes(classesRouteSlots)`. Os testes do `classes` usam slots de mentira (`classesRoutes`, em `classes/__tests__/test-utils.tsx`) e conferem só que a tela diz onde cada um vai e para qual turma; a junção com os componentes verdadeiros é testada em `app/__tests__/classes-slots.test.tsx`, e `grep -rn "@modules/lessons" src/modules/classes` vazio, mais o `depcruise`, guardam a fronteira.

O `assignments` (GUS-159) segue a mesma regra, com a direção de domínio do back (A1 da E5): a alocação depende da aula, da turma e do membro, mas no front o `assignments` depende do **contrato** de `lessons`, `classes` e `people` (os hooks e as chaves gerados em `@api/generated`) e não dos módulos deles: importa só `@modules/auth` e o que o Orval gera, e `lessons`, `classes` e `people` nunca importam `@modules/assignments`. A composição fica em `app/`. O `assignments` tem uma tela própria, Minhas aulas (`/my-lessons`, GUS-161), mas não declara slot: para as telas dos outros módulos ele exporta peças (`NewAssignmentButton`, `NewAssignmentDialog`, `LessonCoverageCard`, `LessonTeacherName`, `MemberAssignmentsCard`, `PendingApplicationsButton` e `PendingApplicationsDialog`), e quem declara o slot é a tela hospedeira, no módulo dela, preenchido pelo `app/`. Hoje o único slot preenchido com uma peça dele é o `renderLessonActions` do `classes`: o `app/classes-slots.tsx` acrescenta o `NewAssignmentButton` depois do `NewLessonButton`, com a turma da tela (`lessonClass`), e a junção é testada em `app/__tests__/classes-slots.test.tsx`. `grep -rn "@modules/assignments" src/modules` vazio, mais o `depcruise`, guardam a fronteira.

Após o login, `/` redireciona para `/profile` ("Meu perfil", módulo `people`). A tela lê o cadastro de quem está logado com `useGetMyProfile` (`GET /members/me`, GUS-122). Campo sem valor aparece como "—" (regra do `DetailsCard` do `people`, a mesma do `DetailsCard` de `@shared/components`, para o qual ele ainda não migrou; o leitor de tela lê "Não informado"), e o cadastro sai do cache quando a página desmonta (`gcTime: 0`), para que outra pessoa que entre na mesma aba não o veja. Os cards de horas ficam em estado vazio (recebem `null`) até a GUS-163 trazer o banco de horas.

**i18n.** Um namespace por módulo, registrado com `registerModuleLocales("people", { "pt-BR": ptBR, "en-US": enUS })` no `index.ts` do módulo. Nos componentes, `useTranslation("people")`.

**Sessão.** `http-client.ts` envia todas as requisições com `credentials: "include"` para que o browser inclua o cookie httpOnly de sessão. Ao receber 401, dispara o evento de `window` `tedi:unauthorized` (`api/` nunca importa `modules/`, então a constante é duplicada de propósito em `shared/lib/session-events.ts`, com um teste garantindo que as duas não divirjam).

O módulo `@modules/auth` (GUS-83) é o dono da sessão no front e expõe:

```ts
type AuthStatus = "loading" | "authenticated" | "anonymous";
interface AuthContextValue {
  status: AuthStatus;
  user: MeResponseDto | null;
  signOut: () => Promise<void>;
}

function AuthProvider(props: { children?: ReactNode }): ReactElement; // sem children, renderiza <Outlet />
function useAuth(): AuthContextValue;
function RequireRole(props: { children?: ReactNode }): ReactElement; // só exige sessão ativa
function RequirePermission(props: { permission: Permission; children?: ReactNode }): ReactElement;
function useCan(permission: Permission, target?: PermissionTarget): boolean;
function SignOutButton(): ReactElement | null;
const authRoutes: RouteObject[]; // rotas públicas do módulo (hoje: "login", "invite" e "reset-password")
const authProtectedRoutes: RouteObject[]; // rotas autenticadas (hoje: "members", com access.manage)
const authMenuItems: MenuItem[]; // "Membros" (grupo people), com access.manage
```

`AuthProvider` carrega a sessão com `GET /auth/me` uma única vez (`staleTime: Infinity`) e entra como rota-layout raiz de `app/router.tsx` — não em `app/providers.tsx`, porque precisa de `useNavigate`/`useLocation`, que só existem dentro do `RouterProvider`. `RequireRole` só exige sessão (é a rota-layout do `AppLayout`). `RequirePermission` protege uma rota (ou subárvore) por permissão: sem sessão vai para `/login?returnTo=<rota>`; sem a permissão renderiza uma página de "sem acesso" no lugar, sem deslogar e sem trocar a URL. Ouve `tedi:unauthorized` e, se já havia sessão autenticada, limpa o cache e redireciona para `/login?returnTo=...&reason=expired`; o 401 inicial de `/auth/me` é tratado como anônimo, não como expiração.

**Permissões (GUS-114).** O `GET /auth/me` (e o `POST /auth/login`) devolve `permissions`: o escopo de cada permissão para o perfil logado (`all`, `own`, `department`, `allocated`, `lessonTeacher` ou `none`), a partir da matriz do back (`tedi-back/docs/PERMISSIONS.md`). O front não repete a matriz: `shared/lib/permissions.ts` expõe `Permission = keyof PermissionsDto` (tipo gerado), `scopeOf` e `can(user, permission, target?)`; `modules/auth` expõe `useCan(permission, target?)` e `<RequirePermission permission>`. Sem `target`, `can` responde "o perfil tem alguma chance?" (menu, rota, botão de criar). Com `target`, `own` compara `target.personId` com o usuário; `department`, `allocated` e `lessonTeacher` seguem `PermissionTarget.serverGrant`, a flag que o back calcula para o recurso (ex.: `canTakeAttendance`, `canConfirmMembers`). `attendance.confirmMember` nunca vale sobre a própria pessoa. A autoridade é sempre o back (RNF-22): esconder botão é só conveniência. ## 5. Integração com a API (Orval)

```
tedi-back                                       tedi-front
1. muda DTO/controller
2. yarn openapi:export → docs/openapi.json
3. CI: openapi:check
4. merge em develop (o template de PR do back tem a seção "Contrato da API": se mudou, abrir a sincronização no front)
5. copiar docs/openapi.json da develop  ─────▶  openapi/openapi.json (manual)
   e rodar `yarn generate` + `yarn format`        src/api/generated/** regenerado
                                               6. CI: typecheck quebra se alguma tela usa campo que sumiu
                                               7. CI: aviso "Contrato OpenAPI desatualizado" enquanto openapi/openapi.json divergir da develop do back
```

O passo 5 continua manual: nenhum workflow copia o contrato. Mas a CI do front avisa quando ele foi esquecido. O passo `Contrato OpenAPI × tedi-back (develop)` do `ci.yml` roda `scripts/check-openapi-drift.mjs`, que baixa `https://raw.githubusercontent.com/projetotedi/tedi-back/develop/docs/openapi.json` (repositório público, sem token) e compara com `openapi/openapi.json` de forma semântica (`operationId`s e `components.schemas`, sem contar a formatação do oxfmt). Se divergir, o job mostra um `::warning::` com as operações que faltam, sobram ou mudaram, e o resumo do job traz a tabela com as operações e os schemas. **O aviso nunca falha o build.** Se o download falhar, aparece "Contrato OpenAPI não verificado".

Para conferir localmente: `yarn openapi:drift`. Para sincronizar (Git Bash): `curl -fsSL https://raw.githubusercontent.com/projetotedi/tedi-back/develop/docs/openapi.json -o openapi/openapi.json && yarn generate && yarn format`. No PowerShell, use `curl.exe` em vez de `curl` e nunca `>` para gravar o JSON (ele sai em UTF-16 ou com BOM e quebra o `JSON.parse`). Não copie do clone local do back sem conferir que ele está na `develop`. O `yarn format` é necessário porque o JSON copiado do back não passa no `format:check`. O PR do front que muda o contrato carrega a cópia de `openapi/openapi.json` e entra depois do PR do back.

Configuração em `orval.config.ts`: `mode: "tags-split"` (um arquivo por tag = um por módulo do back), `client: "react-query"`, `httpClient: "fetch"` com mutator `src/api/http-client.ts`, e um segundo output `client: "zod"`.

O contrato já estava em dia, então não houve `yarn generate`; a tela usa os seis hooks gerados (`useListMyAssignments`, `useListOpenLessons`, `useApplyToLesson`, `useListPendingApplications`, `useApproveApplication` e `useRejectApplication`) e nunca o `confirmAssignment`, que não tem o `ROLE_FULL` da candidatura (C3). Os textos moram no namespace `assignments`, com as chaves por área (`apply`, `pendingApplications`, `myLessons`). Da GUS-159 reaproveitam o `role` ("Professor(a)", "Monitor(a)", por `ASSIGNMENT_ROLE_LABEL_KEYS`), `close` e `retry`; são próprias da candidatura `rolesInline` (o papel no meio da frase), `vacancies` (a linha "Professor(a) 0 de 1 · Monitores 2 de 3", que não é o `coverage` do card Cobertura da aula) e `myLessons.status`, porque em Minhas aulas a pendente é "Aguardando confirmação", como no Figma, e não o "Inscrita" ou "Pendente" de `assignmentStatusLabelKey` (`MY_LESSON_STATUS_LABEL_KEYS`).

    **Minhas aulas.** No topo, os quatro números do Figma (próximas aulas das 4 semanas, confirmadas, aguardando confirmação e aulas com vaga para você), que são o `totals` de `GET /me/assignments` sem período (a API resolve hoje e os 27 dias seguintes), cada um na cor do Figma, com o par de texto e fundo dos tokens de `src/index.css` (nenhum CSS novo). O rótulo tem 16px, e não os 13px do Figma, e o número é `text-3xl`. "Minhas próximas aulas" é a mesma consulta dos números (a chave é a mesma, então é um pedido só) e lista data, horário, turma, aula, papel e situação; a recusada e a cancelada aparecem com a própria tag (F3), fora dos totais; embaixo, o texto que diz o que a lista é e "Ver calendário ›" para `/lessons/calendar`. "Aulas com vaga para candidatura (N)" lê `GET /me/open-lessons`, com data, horário, turma, aula, vagas e o botão **Candidatar-se**, nomeado pela aula e pelo dia ("Candidatar-se à Aula 5 · E-mail do zero, 31/03 (ter)"). A cobertura se escreve "Professor(a) 0 de 1 · Monitores 2 de 3": a parte do professor só aparece enquanto a aula não tem um, a dos monitores quando se espera algum, e sem nenhuma das duas, "Equipe completa" (F4, `lib/coverage.ts`, a mesma regra no modal de pendentes). O dia é "17/03 (ter)" (F5, `formatLessonDay`, lido como data local), diferente do `formatCalendarDate` das outras telas. Cada card tem carregando, vazio e erro com "Tentar de novo", e um erro de releitura com a lista em cache mantém a lista.

    **Candidatar-se à aula.** O modal (640px) mostra o resumo da aula e das vagas, o **Papel na aula** (obrigatório, Monitor(a) antes de Professor(a), descrito como "Apoia os alunos individualmente" e "Conduz a aula"), a **Observação para quem vai aprovar** (opcional, até 500 caracteres, contados sem os espaços das pontas) e o aviso de que a diretoria ou a coordenação decide. O papel sem vaga (`openRoles` da aula, ou um que a API acabou de recusar) fica **desabilitado** e diz o motivo na descrição ("… · Sem vaga nesta aula"), para ele não ficar só na cor; só vem escolhido quando há uma única vaga aberta (F6). Enviar sem papel é recusado no campo, com o foco nele, e não manda nada. **Enviar candidatura** manda `POST /lessons/:id/applications` com `{ role, note }` (observação em branco vira `null`); no sucesso o toast diz o papel e só o dia e o mês, como o Figma ("… como monitor(a) em 31/03.", `formatDayMonth`, o mesmo dos cards da GUS-159), o cache é avisado e o modal fecha, e a aula sai de "com vaga" e entra em "Minhas próximas aulas" como "Aguardando confirmação". Os erros (`lib/application-errors.ts`, que lê o status junto com o código): 409 `ROLE_FULL` desabilita aquele papel, limpa a escolha e recarrega as listas (F7); 409 `ALREADY_APPLIED` e 409 `LESSON_IN_PAST` ou `LESSON_CANCELLED` (a aula não recebe mais candidaturas, C14) viram aviso estático, desligam o envio e recarregam as listas; 404 `LESSON_NOT_FOUND` vira alerta e também recarrega as listas, para a linha da aula que sumiu deixar a tabela de trás; os demais viram alerta; um 400 que aponta `role` ou `note` vai para o campo. Todos levam o foco ao aviso. Em voo, Esc, X e Voltar não fecham e o segundo clique é ignorado. Fechando com Voltar ou Esc o foco volta ao botão que abriu; depois de enviar esse botão sai da tela, e a página leva o foco ao card das aulas com vaga, já com o modal desmontado.

    **Candidaturas pendentes.** O `PendingApplicationsButton` (`secondary`) só existe para quem tem `assignments.review` (diretoria, coordenação e superadmin), e então nada é pedido para os outros; mostra "Candidaturas pendentes (N)", com N o `total` de `GET /applications?status=pending`, e continua visível e habilitado com N = 0 (F9: um botão desabilitado não recebe foco). Ele e o modal usam o mesmo objeto de parâmetros (`PENDING_APPLICATIONS_PARAMS`), então são a mesma consulta e o número nunca diverge da lista (C9); o modal a lê de novo ao abrir, porque quem decide precisa ver o que existe agora. O modal agrupa por aula, na ordem da API, com o título, a turma, o dia, o horário e a cobertura, e por candidatura quem pediu, o papel, a data de envio no fuso do navegador e a observação inteira entre aspas (nunca em Minhas aulas, C11). **Recusar** (`danger-soft`) e **Confirmar** (`primary`) mandam `PATCH /applications/:id/reject` e `/approve`, com o nome da pessoa no `aria-label` e o texto visível dentro dele; enquanto uma ação está em voo as outras linhas e o Fechar ficam desligados, só o botão apertado mostra o carregando, e o modal não fecha. No sucesso, o toast diz quem, o papel e o dia, o cache é avisado e o modal já mostra a fila atualizada: o título e o botão passam de (3) para (2), e a cobertura do bloco soma o confirmado ("Monitores 2 de 3" → "Monitores 3 de 3"). O botão apertado sai com a linha, então o foco vai para o contêiner da lista (um `role="group"` que o foco deixa lido com o título e o novo total) ou, se a fila esvaziou, para a mensagem. A aula cancelada tem a tag "Cancelada" e a linha "Aula cancelada: só é possível recusar.", com Confirmar desligado e ligado a essa linha por `aria-describedby` (a API daria 409 `LESSON_CANCELLED`). Os erros viram alerta no topo, com o foco; 409 `APPLICATION_NOT_PENDING`, 404 `APPLICATION_NOT_FOUND`, 409 `ROLE_FULL` e 409 `LESSON_CANCELLED` dizem que a tela está defasada, e a fila e a cobertura são lidas de novo. Aula passada e cancelada entram na fila, e a candidatura pendente não expira: fica no contador até alguém recusar (C10).

    **Cache (F12).** Candidatar-se (`invalidateAfterApplied`, em `lib/assignment-queries.ts`) invalida `/me/assignments` e `/me/open-lessons` (pelas chaves sem parâmetros, que são o prefixo de qualquer período), `/applications` (o contador de quem revisa) e `/lessons/:id/assignments`, e deixa as listas de aulas quietas, porque a candidatura pendente não ocupa vaga (C1). Aprovar e recusar (`invalidateAfterReviewed`) somam as listas de `/lessons`, o calendário, o detalhe da aula (a cobertura vem em toda resposta de `lessons`) e `/members/:id/assignments`. A alocação direta da GUS-159 usa o `invalidateAfterAssignmentChange`, no mesmo arquivo, que já inclui Minhas aulas, as aulas com vaga e a fila. Tudo é marcado como defasado de uma vez, mas o modal espera só a releitura da fila (o toast e o foco vêm depois dela); o que está atrás dele (a agenda e as aulas com vaga da página, as listas, o detalhe) é lido em segundo plano, para uma leitura lenta ali não segurar os botões. Importar as chaves de `@api/generated/lessons/lessons` é importar o contrato, não o módulo `lessons`, que o `assignments` nunca importa (`grep -rn "@modules/assignments" src/modules/lessons` fica vazio).

    Decisões da GUS-161 (F1 a F12):

    - **F1 (onde montar).** O `PendingApplicationsButton` é exportado pelo `index.ts` e montado provisoriamente no topo de Minhas aulas, só para `assignments.review`. Recusado: `createLessonsRoutes(slots)` agora, que mexeria no que a GUS-155 vai reescrever.
    - **F2 (gênero).** A API não dá o gênero da pessoa: "Professor(a)", "Monitor(a)", "alocado(a)" e, no toast, "como monitor(a)". O Figma escreve "Professora" e "Monitora".
    - **F3 (recusadas e canceladas).** Aparecem em "Minhas próximas aulas" com as tags Recusada e Cancelada, fora dos totais (C6).
    - **F4 (cobertura).** A regra de `coverageParts`, acima, na tabela das vagas e no modal.
    - **F5 (data).** "17/03 (ter)", com `formatLessonDay`, do módulo.
    - **F6 (papel).** Só vem escolhido com uma única vaga aberta; Monitor(a) primeiro, como no Figma.

    - **F8 (Recusar).** Sem confirmação, como no Figma. A recusa é final (C15) e um clique errado não tem desfazer: pode ser um risco para um público idoso, e a decisão é do PO.

    - **F10 (menu).** "Minhas aulas" depois de Calendário, com o rótulo `common:nav.myLessons`; o Figma não mostra o item.
